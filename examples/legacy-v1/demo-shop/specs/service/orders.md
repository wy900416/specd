# Orders Service

## Responsibility

Owns the order aggregate and its state machine. It is the source of truth for
order status; it does not store payment instrument data.

## Data ownership

- `order`: only this service writes it; support tooling reads it.
- `order_event`: append-only transition log owned by this service.

## Interfaces

- Exposes `orders-api` for checkout clients.
- Calls `payments-api` to authorize a payment.

## Dependencies

- `payments` — synchronous authorization. If payments is unavailable, the order
  stays `pending` and the caller receives a retryable error.

## Behaviour and failure modes

- Create order -> persist `pending` -> call payments -> on success persist
  `confirmed`; on failure persist `rejected` with a reason.
- The create call is idempotent on the client-supplied `Idempotency-Key`.
- A timeout from payments is treated as unknown; the order is not confirmed until
  a follow-up query resolves the authorization state.

## Requirements

### REQ-ORD-001: Create an order idempotently

- **Priority:** must
- **Normative:** true
- **Given:** a client submits the same `Idempotency-Key` twice
- **When:** both requests reach the service
- **Then:** exactly one order is created and both responses carry the same order id

### REQ-ORD-002: Do not confirm without authorization

- **Priority:** must
- **Normative:** true
- **Given:** an order in `pending`
- **When:** the payment authorization fails or times out
- **Then:** the order is not confirmed and the caller receives a reason

## Constraints

- `security-baseline` and `latency-budget` apply to this service.
